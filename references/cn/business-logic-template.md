# 项目知识层模板（v1.4.2）

> **定位**：知识层是核心，传统 7 套文档（01–07）只是知识层的不同展示视图。7 套文档模板见 `references/cn/document-templates.md`，其文件名、编号、路径保持不变。
>
> **追溯链路**：
>
> ```
> 业务问题 → 业务能力 → 业务规则 → 入口/API → 调用链 → 数据变化 → 外部依赖 → 源码文件/符号 → 测试
> ```
>
> **双向索引**：BL 条目 → 源码（各 BL 条目的「源码证据」「数据变化」「触发入口」「外部影响」）与源码 → BL（`00-源码索引.md`）互为反向索引，两者必须一致。
>
> **查询模式（只读）**：只读的意思是**不修改文件**，不是不读源码。查询模式允许读取源码、`git diff` 与相关测试做即时核实，但**不得修改知识层或源码**；正常路径为「问题 → 知识地图 → BL → 直接回答」，BL 缺失 / 时效状态非「最新」/ 证据不足时走「BL → 源码索引（定位符号与文件）→ 读取实际源码 → 只读核实 → 回答」，**不得因为文档过期就要求用户先去跑同步**。
>
> **作者获取优先级**：以 `SKILL.md` 的「作者信息获取」章节为唯一权威（四级：① 用户明确提供的作者 → ② 本地默认作者 `Soonkeira`（https://github.com/Soonkeira） → ③ Git 提交作者 `git log -1 --format=%an` → ④ 置空）。**严禁**把机器账户名（`$env:USERNAME` / `whoami`）当作作者。
>
> **示例标注**：本文件模板中的所有示例内容均为占位示例，必须明确标注「示例（占位，非项目事实）」，实际生成时替换为真实分析结果。
>
> **本文件包含**：
> 1. 知识地图模板 `00-项目知识地图.md`
> 2. 源码索引模板 `00-源码索引.md`
> 3. 业务逻辑条目模板 `business/BL-<NNN>-<业务名称>.md`
> 4. 状态定义与判定规则
> 5. 追溯性正反例
> 6. 示例内容标注规则

## 二、验证基线

| 字段 | 值 |
|------|-----|
| last_verified_commit | `<commit 哈希>` |
| 验证日期 | YYYY-MM-DD |
| 工作区状态 | `Clean` / `Dirty`（判定命令 `git status --porcelain`：无输出即 `Clean`） |
| 验证状态 | `正式基线` / `临时工作区分析` |
| 正式基线 | `<commit 哈希>`（仅工作区 `Clean` 时重新验证后推进；`Dirty` 时保持上一次正式基线，不推进） |
| 时效判定是否可用 | 可用 |
| 时效判定方式 | 变更文件集（提交部分 `git diff --name-status -M <last_verified_commit>..HEAD` ∪ 工作区部分 `git status --porcelain`）与各 BL 条目的「源码证据」「核心执行流程」「数据变化」「触发入口」「外部影响」「前置条件」「相关测试」做多层影响判定（见 4.2 节） |
| traditional_docs_status | `current` / `outdated` / `provisional` |
| traditional_docs_working_tree | `Clean` / `Dirty` / `未发现（无 Git）` |
| traditional_docs_generated_from_commit | `<7 套传统文档生成时的 commit 哈希>` |

> **验证基线只在工作区干净时推进**：工作区 `Dirty` 时可以分析、可以回答、可以更新 BL 内容，但**不得推进 `last_verified_commit`**、**不得把条目标记为 `最新`**，该条时效状态记 `临时工作区分析`。工作区恢复 `Clean` 后，这些 `临时工作区分析` 条目必须无条件重新纳入本轮 affected set 并重新读取源码验证，全部重验完成前不得标记 `最新`、不得推进正式基线（见 4.2 第四步）。理由：BL 可能是根据**未提交的工作区代码**生成的，若用户随后用 `git restore` 丢弃这些改动，HEAD 没变、工作区也干净，但 BL 描述的是一份**已不存在的实现**，系统却会认为它「最新」。
>
> **传统文档新鲜度**：同步模式**不更新** 7 套传统文档，所以同步之后（且代码已变化）`traditional_docs_status` 应为 `outdated`，直到重新运行生成模式才回到 `current`。`traditional_docs_status` 三值：`current` = 传统文档由 **Clean** 工作区生成，且当前知识层未发现比其更新的代码变化；`outdated` = 代码/知识层已经发生变化，但传统 7 套文档尚未重新生成；`provisional` = 传统文档是在 **Dirty** 工作区下生成，内容可能包含未提交代码，**不能把 HEAD commit 当作唯一来源**。生成模式：Clean → `current` + `traditional_docs_working_tree` = `Clean`；Dirty → `provisional` + `traditional_docs_working_tree` = `Dirty`；同步模式（代码变化但不重新生成 01–07）→ `outdated`；重新运行生成模式同样按上述 Clean / Dirty 规则判定。
> `traditional_docs_status` / `traditional_docs_generated_from_commit` / `traditional_docs_working_tree` **统一记录在 `00-项目知识地图.md`**；**`00-项目知识地图.md` = 文档状态中心**。01–07 仍是生成产物，同步模式**不去修改**它们，以保持同步模式轻量；判断传统文档是否最新应读知识地图的这三个字段。

**三种基线状态必须区分（三个互斥分支）**：

- **分支 A — 无 Git（或 HEAD 无效）**：使用下方「无 Git 或无有效 HEAD 时的降级写法」；时效状态记 `未发现（无 Git 基线）`；每次运行需**全量复核**；**不得编造 commit 哈希**。
- **分支 B — 有 Git，但正式基线尚未建立**（`last_verified_commit` 为空 / `正式基线` = `未建立`）：见下方「分支 B 的取值」。
- **分支 C — 已有正式基线**：正常增量同步（见 4.2、4.5）。

**分支 B 的取值（示例（占位，非项目事实））**：

| 字段 | 值 |
|------|-----|
| last_verified_commit | 未建立 |
| 正式基线 | 未建立 |
| 验证状态 | `临时工作区分析` |
| 工作区状态 | `Dirty` |

> **分支 B 不执行任何 `<base>..HEAD` 形式的增量 diff**（此时没有合法的 `<base>`），必须执行**全量复核**：
> - 工作区 **`Clean`** → 全量复核后建立正式基线：`last_verified_commit` = 当前 HEAD、`正式基线` = 当前 HEAD、`验证状态` = `正式基线`、`工作区状态` = `Clean`、本次验证的条目 = `最新`。
> - 工作区 **`Dirty`** → 保持 `验证状态` = `临时工作区分析`、`工作区状态` = `Dirty`；`last_verified_commit` 与 `正式基线` 保持 `未建立`；**不建立正式基线、不标记 `最新`**。
>
> **严禁**把「有 Git 但正式基线未建立」写成 `未发现（无 Git 基线）`——Git 实际存在，这两件事必须区分。

## 三、编号登记（ID Registry）

| 项目 | 值 |
|------|-----|
| 当前最大编号 | `BL-006` |
| 下一个可用编号 | `BL-007` |
| 已废弃编号（tombstone，永不复用） | `BL-006`（原「订单批量导出」，YYYY-MM-DD 废弃） |

> 取号规则：新条目编号 = **历史最大 BL 编号 + 1**（当前最大为 `BL-006` → 下一个新条目是 `BL-007`）。
> 删除的编号**永久 tombstone、永不复用**；**允许因删除产生跳号**（跳号正常，不是错误）。**稳定 ID 比编号连续重要得多**。
> **为什么必须登记**：没有编号登记就无法保证「永不复用」——当最高编号的条目被删除时，只看当前最大号会退回去复用已废弃的号；取号前必须先读本表。

### 1.3 填写要求

- **分析范围**必须真实反映本次扫描行为：写了「已扫描」就必须真的读过，跳过敏感文件与依赖目录的原因要写明。
- **验证基线**是全局基线，`last_verified_commit`、验证日期与「最近一次增量分析」必须来自真实 Git 命令输出与真实分析结果（变更文件数含未提交修改）；无 Git 时按降级写法填写，并明确「每次运行需全量复核」；**有 Git 但正式基线尚未建立（分支 B）时必须全量复核，不得执行任何 `<base>..HEAD` 形式的增量 diff**（见「验证基线」章节的分支说明）。
- **验证基线只在工作区干净时推进**：先跑 `git status --porcelain` 判定 `工作区状态`（无输出 = `Clean`，有输出 = `Dirty`）。`Clean` 时允许重新验证后推进 `last_verified_commit` 与 `正式基线`，并把重新验证过的条目标记 `最新`；`Dirty` 时**不得推进 `last_verified_commit`**、**不得标记 `最新`**，`验证状态` 记 `临时工作区分析`。
- **传统文档新鲜度**：`traditional_docs_status` 记三值之一——`current`（传统文档由 **Clean** 工作区生成，且当前知识层未发现比其更新的代码变化）/ `outdated`（代码/知识层已经发生变化，但传统 7 套文档尚未重新生成）/ `provisional`（传统文档是在 **Dirty** 工作区下生成，内容可能包含未提交代码，**不能把 HEAD commit 当作唯一来源**）；`traditional_docs_working_tree` 记 `Clean` / `Dirty` / `未发现（无 Git）`；`traditional_docs_generated_from_commit` 记 7 套传统文档生成时的 commit。生成模式：Clean → `current` + `Clean`，Dirty → `provisional` + `Dirty`；同步模式不更新 7 套传统文档，所以同步之后（且代码已变化）必须记 `outdated`，直到重新运行生成模式才回到 `current`。
- **传统文档状态只在知识地图维护**：`traditional_docs_status` / `traditional_docs_generated_from_commit` / `traditional_docs_working_tree` **统一记录在 `00-项目知识地图.md`**；**`00-项目知识地图.md` = 文档状态中心**。01–07 仍是生成产物，同步模式**不去修改**它们，以保持同步模式轻量；判断传统文档是否最新应读知识地图的这三个字段，**不为 01–07 增加独立 stale 字段**。
- **编号登记（ID Registry）**必须与业务能力索引、BL 条目一致：`当前最大编号` 取历史最大 BL 编号（含已废弃编号在内的历史最大值），`下一个可用编号` = 当前最大编号 + 1，`已废弃编号` 逐个列出 tombstone 及其废弃日期。已废弃编号不得同时出现在业务能力索引中（本表为示例（占位，非项目事实），生成时必须替换为真实编号）。
- **业务能力索引**按业务域分组，每组一个表格，列固定为 `| ID | 业务能力 | 描述 | 证据状态 | 时效状态 |`，不得增删列、不得改列名，不得把两个状态合并到一列。
- **业务能力索引按业务域分组展示**：分组标题只写业务域名称，**不得带任何编号范围**；业务域与各 BL 条目头部的 `**业务域**` 字段必须一致。
- **未发现 / 推断条目汇总**只列证据状态为 `推断` 或 `未发现` 的条目，说明其证据缺口；该表只写证据状态，不写时效状态。
- **常见业务问题索引**必须把用户的真实提问映射到 BL 编号，链接可直接跳转到对应条目。
- **禁止只写项目简介**：没有业务能力索引的知识地图视为未完成，不得作为交付物。

## 三、业务逻辑条目模板 `business/BL-<NNN>-<业务名称>.md`

### 3.1 输出路径与编号规则

- 中文：`Doc/<项目名称>/cn/business/BL-<NNN>-<业务名称>.md`
- 英文：`Doc/<项目名称>/en/business/BL-<NNN>-<business-name>.md`
- 同一业务逻辑在各语言下**编号一致**。

**BL 编号规则**：`BL-` + 三位数字，取号规则为**历史最大 BL 编号 + 1**：`BL-001`、`BL-002`、`BL-003`……

- **取号规则**：新条目编号 = **历史最大 BL 编号 + 1**（当前最大是 `BL-006` → 下一个新条目是 `BL-007`）。历史最大编号与已废弃编号记录在知识地图的「编号登记（ID Registry）」章节，取号前必须先读该章节。
- **删除即 tombstone**：被删除的编号**永久保留占位、永不复用**；例如 `BL-006` 删除后永久保留占位，下一个新条目是 `BL-007`（= 历史最大号 + 1）。注意本例中历史最大号本身就是已废弃的号：只看在册条目的最大号会算成 `BL-005`，从而错误复用 `BL-006`——这正是必须维护「编号登记」的原因。
- **允许跳号**：因删除产生的跳号是正常现象，不是错误；**不得为了编号连续而复用已废弃的编号**。
- **稳定 ID 比编号连续重要得多**：已有条目的编号一旦分配就不再变动，不因新增、删除或重新分类而改变；**永不复用、永不重排**。
- **不按业务域分段**：业务域是 metadata，写在 BL 条目头部的 `**业务域**：<业务域名称>` 字段，不参与编号。
- 业务域重新分类时**只改 `**业务域**` 字段，绝不改 ID**；知识地图按业务域分组展示时，分组标题只写业务域名称，不带任何编号范围。
- 每次取号或废弃编号后，必须同步更新知识地图「编号登记（ID Registry）」的 `当前最大编号` / `下一个可用编号` / `已废弃编号` 三项。

### 3.2 BL 粒度判定

- **BL = 用户/业务可感知的业务能力或用例（Use Case）**，不是 Controller 方法，也不是技术函数。
- 多个 API 如果只是同一个业务能力的不同入口 → **可以属于同一个 BL**。
- 同一个 API 如果存在完全不同的业务结果、事务边界或业务生命周期 → **可以拆成多个 BL**。
- **CRUD 不默认「一接口一个 BL」**。
- 技术工具函数、Repository CRUD、DTO 转换**不独立成为 BL**。
- BL 以**稳定业务语义**命名（如「创建订单」「取消订单」「审核退款」「分配公网 IP」），不以技术动作命名。
- **重构 Controller / Service 层次不应导致 BL 编号改变**（ID 跟着业务语义走，不跟代码结构走）。
- **目的**：保证不同模型、不同时间运行生成的知识体系规模稳定（避免一次 28 条、下次 64 条）。

**判定示例**：`POST /users`、`GET /users/:id`、`PUT /users/:id`、`DELETE /users/:id` 若属于同一业务能力「用户管理」，可合并为一个 BL；但若「注销用户」有独立的事务边界与生命周期，则单独成为一条。

## 四、状态定义与判定规则

### 4.1 证据状态（evidence status）

**由模型判断**，每个 BL 条目与知识地图中的每条索引**只能四选一**：

| 证据状态 | 含义 | 判定依据 |
|----------|------|----------|
| `已验证` | 已从源码中直接确认 | 有明确源码证据（文件 → 符号），调用链、数据变化、分支均已读到对应实现 |
| `部分验证` | 主要结论已确认，部分环节未确认 | 核心链路已确认，但分支、异常、外部影响或数据变化中有未读到实现的部分 |
| `推断` | 由命名、目录结构、配置或文档推断 | 未找到直接实现证据，只能靠结构或命名推断，必须写出推断依据 |
| `未发现` | 未找到任何证据 | 未找到入口、实现、测试或数据访问代码 |

### 4.2 时效状态（freshness）

**时效状态以 Git 变更检测为基础，并结合 Source Map 与多层影响分析判定**——不是纯 Git 机械判定，也不是纯模型判断，取值只有四个：

- **Git 负责 Change Detection**：HEAD、baseline、变更文件集、重命名/删除、工作区 `Clean`/`Dirty` —— 纯机械结果。
- **影响分析负责 Impact Analysis**：符号影响、API 影响、数据影响、配置影响、调用链影响 —— 不是纯 Git 判断。
- **两者共同得到 Freshness Status**。

| 时效状态 | 含义 |
|----------|------|
| `最新` | 工作区 `Clean`，且该条证据相关文件与符号，在「最后验证版本」commit 与当前工作区之间没有变化 |
| `⚠ 可能过期` | 上述范围内存在变化，且该条本次未重新验证 |
| `临时工作区分析` | 本次分析基于 `Dirty` 工作区（未推进正式基线），该条结论只对当前工作区有效 |
| `未发现（无 Git 基线）` | 无 Git 或无有效 HEAD，无法做时效判定（见 4.4） |

> 标记 `最新` 的前提是工作区 `Clean`：`git status --porcelain` 有输出时，即使该条已重新验证且未命中任何影响层，也只能记 `临时工作区分析`（见 4.5）。

**第一步：确定变更文件集（必须包含未提交修改）**

变更文件集 = **提交部分** ∪ **工作区部分**：

| 部分 | 命令 | 覆盖范围 |
|------|------|----------|
| 提交部分 | `git diff --name-status -M <base>..HEAD` | 基线之后已提交的变更，`-M` 用于检测重命名 |
| 工作区部分 | `git status --porcelain` | 已暂存、未暂存、未跟踪（`??`）的变更 |

> **不能只看 `<base>..HEAD`**：代码可能已经改完但尚未提交，只比较 commit 会漏判过期，工作区部分必须一并纳入。
> 未跟踪文件只在本次分析范围内才计入；跳过 `.gitignore` 忽略项与默认跳过目录（依赖、构建产物、缓存等）。
> **「变更文件集含未提交修改」与「工作区干净才推进基线」不冲突**：前者用于**检测哪些条目受影响**（`Dirty` 时同样要把未提交改动纳入影响判定，否则会漏判过期），后者用于**决定能否推进正式基线**（`Dirty` 时不得推进 `last_verified_commit`，也不得标记 `最新`）。

**第二步：多层影响判定**（命中任意一层即判受影响，并记录命中依据）：

| 层 | 判定方式 |
|----|----------|
| a. 路径层 | 变更文件 ∩ 该条「源码证据」路径 |
| b. 符号层 | diff 中修改/新增/删除的符号 ∩ 该条「核心执行流程」调用链符号、「源码证据」符号列 |
| c. 数据层 | 变更涉及的表名/字段名/迁移 ∩ 该条「数据变化」 |
| d. 接口层 | 变更涉及的路由/接口/入口签名 ∩ 该条「触发入口」 |
| e. 配置层 | 变更涉及的配置项/环境变量 ∩ 该条「外部影响」「前置条件」 |
| f. 测试层 | 变更涉及的测试文件 ∩ 该条「相关测试」→ 标记「测试证据待复核」（业务逻辑未必失效） |
| g. 重命名/删除 | 证据文件被重命名 → 「路径失效需修复」；被删除 → 「证据文件已删除，需重新验证或废弃该条目」 |

**额外报告**：若变更文件是某 BL 调用链中符号的定义文件，但不在该 BL「源码证据」里 → 标注「证据清单缺失，需补全」。

**第三步：得出结论**

- 命中任意一层且该条本次未重新验证 → 时效状态置 `⚠ 可能过期`；全部未命中 → 时效状态为 `最新`。
- **但推进正式基线与标记 `最新` 都以工作区干净为前提**：`git status --porcelain` 有输出（`Dirty`）时，不得推进 `last_verified_commit`、不得标记 `最新`，时效状态记 `临时工作区分析`。
- 工作区 `Dirty` 只影响**基线推进**与**`最新` 标记**，不影响分析与回答：该条仍可分析、可回答、可更新内容。

**第四步：强制恢复 provisional 条目（工作区 `Clean` 时，必做）**

受影响集合（affected BL）必须取**并集**，而不只是影响分析的命中结果：

```text
affected BL =
  影响分析（Git 变更检测 + Source Map + 多层判定）命中的 BL
  ∪ 所有 freshness_status = 临时工作区分析 的 BL（当前工作区为 Clean 时）
```

- **只要某 BL 当前时效状态为 `临时工作区分析`，在后续工作区变为 `Clean` 时，该 BL 必须无条件加入本轮 affected set 并重新读取当前源码验证，不依赖 `<baseline>..HEAD` 是否存在 diff。**
- 这些 provisional BL **全部重新验证完成前**：**不得标记 `最新`**、**不得认为知识层已经恢复一致**、**不得推进正式基线**。
- 重新验证后按实际情况定档：内容与当前 `Clean` 源码一致 → `最新`；无法确认 → 按实际情况记 `部分验证` / `推断` / `⚠ 可能过期`；`00-源码索引.md` 同步刷新。
- **为什么必要（`git restore` 场景）**：正式 baseline = `abc123` → 工作区修改代码（`Dirty`）→ 同步后 BL 正文根据 `Dirty` 代码更新、时效状态 = `临时工作区分析` → 用户 `git restore` 丢弃修改 → HEAD 仍为 `abc123`、工作区重新 `Clean`、`git diff abc123..HEAD` 为空。此时 BL 正文可能仍描述已经不存在的临时代码，而常规 Git 影响分析**无法发现**（因为没有 diff）；只有按本规则把 `临时工作区分析` 条目强制重新纳入 affected set，才能发现并修正这类知识污染。

辅助命令：`git rev-parse HEAD`（当前基线）、`git log --oneline <base>..HEAD`（改动概览）、`git status --porcelain`（未提交变更）、`git rev-list --count HEAD`（版本号第四段）、`git log -1 --format=%an`（Git 提交作者）。

### 4.3 两个字段相互独立

- 证据状态与时效状态是**互相独立**的两个字段，**严禁混用、严禁合并书写**：`已验证` 表示「当时读到过实现」，不代表内容没过期；`⚠ 可能过期` 表示「代码改过了」，不代表当初的证据是错的。
- 知识地图用**两列分别显示**：`| ID | 业务能力 | 描述 | 证据状态 | 时效状态 |`，证据状态列只写四选一取值，时效状态列只写四选一取值。
- **严禁**把两个状态合并到同一列或同一行书写：不得用前缀、斜杠、括号等方式把证据状态与时效状态拼成一条，两者必须各占一列或各占一节。
- BL 条目内同样分节书写：「13. 证据状态」与「14. 时效状态」各写各的。

### 4.4 无 Git 或无有效 HEAD 的降级

- **本节只适用于分支 A（无 Git 或无有效 HEAD）**：有 Git 但正式基线尚未建立（`last_verified_commit` / `正式基线` = `未建立`）属于**分支 B**，必须走全量复核并保留 `临时工作区分析`，**严禁**写成 `未发现（无 Git 基线）`。
- 不做时效判定，时效状态记 `未发现（无 Git 基线）`。
- 在知识地图「验证基线」章节说明时效判定不可用，并说明**每次运行需全量复核**。
- **不得编造 commit 哈希**，也不得用日期、文件时间戳冒充 commit。

### 4.5 增量维护基线

- **全局基线**：写在 `00-项目知识地图.md` 的「验证基线」章节，字段为 `last_verified_commit` + 验证日期 + `工作区状态` + `验证状态` + `正式基线`。
- **单条基线**：写在每个 BL 条目的「最后验证版本」章节，字段为 Git commit + 验证日期 + 工作区状态。
- **只在工作区干净时推进基线**，判定命令 `git status --porcelain`：
  - 工作区 `Clean`（无输出）：允许重新验证后推进 `last_verified_commit` 与 `正式基线`，并把重新验证过的条目标记 `最新`。
  - 工作区 `Dirty`（有输出）：可以分析、可以回答、可以更新 BL 内容，但**不得推进 `last_verified_commit`**、**不得标记 `最新`**；该条时效状态记 `临时工作区分析`，条目的「最后验证版本」保留正式基线 commit（分支 B 尚无正式基线时写 `未建立（有 Git，但尚未建立正式基线）`，**不得编造 commit**）并追加一行「本次分析基于未提交工作区，未推进正式基线」。
  - **理由**：BL 可能是根据**未提交的工作区代码**生成的；若用户随后用 `git restore` 丢弃这些改动，HEAD 没变、工作区也干净，但 BL 描述的是一份**已不存在的实现**，系统却会认为它「最新」。
- 增量更新时，只复核受影响的条目（按 4.2 的多层判定），未受影响条目的「最后验证版本」保持原值，不刷新为当前 HEAD。
- **affected set 必须包含全部 `临时工作区分析` 条目**：工作区为 `Clean` 时，本轮 affected set = 影响分析命中的 BL ∪ 所有时效状态仍为 `临时工作区分析` 的 BL（见 4.2 第四步）；这些条目**全部重新验证完成前不得推进 `last_verified_commit`**，也不得标记 `最新`、不得认为知识层已经恢复一致。
- **正式基线尚未建立时（分支 B）不执行任何 `<base>..HEAD` 形式的增量 diff**（此时没有合法的 `<base>`），必须执行**全量复核**：工作区 `Clean` → 复核后建立正式基线（`last_verified_commit` = `正式基线` = 当前 HEAD、`验证状态` = `正式基线`、`工作区状态` = `Clean`、本次验证的条目 = `最新`）；工作区 `Dirty` → 保持 `last_verified_commit` 与 `正式基线` 为 `未建立`、`验证状态` 为 `临时工作区分析`，**不建立正式基线、不标记 `最新`**。
- 每次增量分析结束后，在知识地图「验证基线」的「最近一次增量分析」中记录：基线 commit、分析日期、变更文件数（含未提交）、受影响 BL、已重新验证的 BL、仍标记过期的 BL。
- 变更文件集必须包含未提交修改（`git status --porcelain`），**不得只比较 `<base>..HEAD`**；这是**影响检测**规则，与上面「工作区干净才推进基线」的**基线推进**规则不冲突（见 4.2 第一步与第三步）。

### 4.6 禁止事项

- **禁止把模型推断包装成事实**：推断内容必须显式标注 `状态：推断` 并写明推断依据，不得使用「系统会」「一定是」这类断言语气。
- 禁止编造业务事实、编造 commit 哈希、表名、接口、测试用例或业务规则；时效判定必须来自真实 Git 命令输出，**禁止在时效判定里编造 commit 哈希**。
- **禁止在 `Dirty` 工作区推进正式基线或标记 `最新`**：未提交改动可能被 `git restore` 丢弃，届时 BL 描述的是一份已不存在的实现（见 4.5）。
- **禁止在存在未重新验证的 `临时工作区分析` 条目时标记 `最新`**：工作区恢复 `Clean` 后，这些条目必须无条件重新纳入 affected set 并重新读取源码验证（见 4.2 第四步）；全部重验完成前**不得标记 `最新`**、**不得认为知识层已经恢复一致**、**不得推进正式基线**。
- **禁止在正式基线未建立时编造 commit，也禁止误写成 `未发现（无 Git 基线）`**：分支 B（有 Git，但正式基线尚未建立）的「最后验证版本」写 `未建立（有 Git，但尚未建立正式基线）`（见 3.4 第 15 节、「验证基线」章节与 4.4）。
- **禁止复用已废弃的 BL 编号**：删除即 tombstone，取号一律用「历史最大编号 + 1」，并同步更新知识地图「编号登记（ID Registry）」（见 3.1）。
- **严禁**把「有 Git 但正式基线未建立」（分支 B）写成 `未发现（无 Git 基线）`：Git 实际存在，只是正式基线尚未建立，两者必须区分（见「验证基线」章节与 4.4）。
- 禁止删除现有 7 套文档模板、大规模重命名、引入运行时依赖，禁止引入数据库、Web UI、RAG 或向量数据库。

## 五、追溯性正反例

### 5.1 业务规则

- ❌ 不能只写：「系统会检查用户权限。」
- ✅ 应写成：「系统在 `PermissionService.checkPermission()` 中检查当前用户是否具有该资源的操作权限。」

### 5.2 调用链

- ❌ 不能只写：「调用订单服务完成取消。」
- ✅ 应写成：`OrderController.cancel()` → `OrderService.cancelOrder()` → `Order.cancel()` → `InventoryService.release()` → `OrderRepository.save()`

### 5.3 数据变化

- ❌ 不能只写：「更新订单状态。」
- ✅ 应写成：`orders.status: PENDING_PAYMENT → CANCELLED`，同一事务内同时更新 `orders.updated_at`。

### 5.4 测试

- ❌ 不能只写：「已有单元测试覆盖。」
- ✅ 应写成：「`tests/order/cancel.spec.ts` → `should cancel pending order` 覆盖正常取消路径。」（未找到测试时写「未发现对应自动化测试。」）

### 5.5 推断标注

- 只能靠结构推断时（例如只看到 `XxxRepository` 命名而没读到实现），必须显式标注 `状态：推断`，并写明推断依据（目录结构 / 命名 / 配置项 / 迁移脚本）。
- 推断内容不得写入「源码证据」表的 `路径 → 符号` 列冒充直接证据；如需保留，另起一行标注「（推断）」。
