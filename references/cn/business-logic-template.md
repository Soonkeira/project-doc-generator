# 项目知识层模板（v1.3.0）

> **定位**：知识层是核心，传统 7 套文档（01–07）只是知识层的不同展示视图。7 套文档模板见 `references/cn/document-templates.md`，其文件名、编号、路径保持不变。
>
> **追溯链路**：
>
> ```
> 业务问题 → 业务能力 → 业务规则 → 入口/API → 调用链 → 数据变化 → 外部依赖 → 源码文件/符号 → 测试
> ```
>
> **双向索引**：BL 条目 → 源码（各 BL 条目的「源码证据」「数据变化」「触发入口」「外部影响」）与源码 → BL（`00-源码索引.md`）互为反向索引，两者必须一致。
>
> **作者获取优先级**：以 `SKILL.md` 的「作者信息获取」章节为唯一权威（四级：① 用户明确提供的作者 → ② 本地默认作者 `Soonkeira`（https://github.com/Soonkeira） → ③ Git 提交作者 `git log -1 --format=%an` → ④ 置空）。**严禁**把机器账户名（`$env:USERNAME` / `whoami`）当作作者。
>
> **示例标注**：本文件模板中的所有示例内容均为占位示例，必须明确标注「示例（占位，非项目事实）」，实际生成时替换为真实分析结果。
>
> **本文件包含**：
> 1. 知识地图模板 `00-项目知识地图.md`
> 2. 源码索引模板 `00-源码索引.md`
> 3. 业务逻辑条目模板 `business/BL-<NNN>-<业务名称>.md`
> 4. 状态定义与判定规则
> 5. 追溯性正反例
> 6. 示例内容标注规则

- **分析范围**必须真实反映本次扫描行为：写了「已扫描」就必须真的读过，跳过敏感文件与依赖目录的原因要写明。

- **未发现 / 推断条目汇总**只列证据状态为 `推断` 或 `未发现` 的条目，说明其证据缺口；该表只写证据状态，不写时效状态。
- **常见业务问题索引**必须把用户的真实提问映射到 BL 编号，链接可直接跳转到对应条目。
- **禁止只写项目简介**：没有业务能力索引的知识地图视为未完成，不得作为交付物。

- 「未覆盖的源码文件」只列**重要文件**（入口、服务、数据访问、配置、迁移脚本），并写明未覆盖原因；依赖目录、构建产物、缓存与生成物不列。
- **增量同步时一并更新**：新增、删除 BL 条目或修改其证据类章节后，必须重新汇总本索引；同步模式只写知识层，不改 7 套传统文档。
- 禁止把推断出的归属写成确定归属：无法从代码确认的引用关系写入「覆盖范围与限制」，并标注推断依据。

### 3.1 输出路径与编号规则

- 中文：`Doc/<项目名称>/cn/business/BL-<NNN>-<业务名称>.md`
- 英文：`Doc/<项目名称>/en/business/BL-<NNN>-<business-name>.md`
- 同一业务逻辑在各语言下**编号一致**。

**BL 编号规则**：`BL-` + 三位数字，按**首次建立顺序递增**：`BL-001`、`BL-002`、`BL-003`……

- 编号**永不复用、永不重排**：已有条目的编号一旦分配就不再变动，不因新增、删除或重新分类而改变。
- 条目删除后其编号作废；新建条目取当前未使用的**最小编号**（例如 `BL-003` 已随条目删除而作废，则下一个新条目使用 `BL-003`）。
- **不按业务域分段**：业务域是 metadata，写在 BL 条目头部的 `**业务域**：<业务域名称>` 字段，不参与编号。
- 业务域重新分类时**只改 `**业务域**` 字段，绝不改 ID**；知识地图按业务域分组展示时，分组标题只写业务域名称，不带任何编号范围。

### 3.3 各章节填写要求与正反例

**15 个固定章节的顺序与标题逐字一致，不得增删、不得改名、不得调整顺序。**

头部 metadata 块（项目名称 / 业务域 / 作者 / 日期 / 版本 + 变更日志）不计入这 15 个章节。

| # | 章节 | 填写要求 |
|---|------|----------|
| 1 | 业务说明 | 从用户/业务视角解释该业务解决什么问题、对谁有价值、在什么场景被使用；**不要一开始就描述代码**。 |
| 2 | 触发入口 | 写出真实入口：HTTP API / RPC / CLI / 定时任务 / MQ Consumer / Event Handler / UI 操作 / 内部方法调用。没有入口证据时写「未发现」。 |
| 3 | 前置条件 | 执行前必须满足的真实条件（数据状态、权限、外部系统可用性、配置开关）；不要写「系统正常运行」这类空话。 |
| 4 | 业务规则 | 什么情况下允许执行、什么情况下拒绝、状态转换条件、权限要求、数值限制、生命周期限制。 |
| 5 | 核心执行流程 | 必须是**真实调用链**，用箭头逐层列出到数据访问层为止；**禁止只写笼统描述**（如「校验后更新订单」）。 |
| 6 | 关键分支 | if / switch / 状态机 / 异常分支等**真正影响业务行为**的条件，说明每个分支走向的差异。 |
| 7 | 数据变化 | 修改哪些表、哪些字段、创建/删除什么数据、状态如何变化、是否有事务。 |
| 8 | 外部影响 | MQ / Redis / 第三方 API / 文件系统 / 缓存 / 对象存储 / 支付系统 / 短信邮件等；**没有则明确写「未发现」**。 |
| 9 | 异常与失败路径 | 只写**已验证**的异常条件与处理结果；未验证的异常不要写。 |
| 10 | 源码证据 | 表格两列 `\| 类型 \| 来源 \|`，类型含 Controller / Service / Domain / Repository / Model / 表 / 配置项，来源写成 `路径 → 符号`。 |
| 11 | 相关测试 | 真实测试文件与测试方法；没有就写「未发现对应自动化测试。」**禁止虚构测试**。 |
| 12 | 关联业务 | 关联的 BL 编号与名称（上游触发、下游依赖、共享数据）。 |
| 13 | 证据状态 | 四选一：`已验证` / `部分验证` / `推断` / `未发现`，由模型判断。 |
| 14 | 时效状态 | Git 机械判定，三选一：`最新` / `⚠ 可能过期` / `未发现（无 Git 基线）`；**禁止与证据状态合并书写**，也禁止用模型判断代替 Git 判定。 |
| 15 | 最后验证版本 | Git commit + 验证日期（单条基线）；无 Git 时写「未发现（无 Git 基线）」。 |

**第 5 节「核心执行流程」的写法要求**：

> 以下为模板示例（占位，非项目事实），实际生成时替换为真实分析结果。

OrderController.cancel()
↓

## 四、状态定义与判定规则

### 4.1 证据状态（evidence status）

**由模型判断**，每个 BL 条目与知识地图中的每条索引**只能四选一**：

| 证据状态 | 含义 | 判定依据 |
|----------|------|----------|
| `已验证` | 已从源码中直接确认 | 有明确源码证据（文件 → 符号），调用链、数据变化、分支均已读到对应实现 |
| `部分验证` | 主要结论已确认，部分环节未确认 | 核心链路已确认，但分支、异常、外部影响或数据变化中有未读到实现的部分 |
| `推断` | 由命名、目录结构、配置或文档推断 | 未找到直接实现证据，只能靠结构或命名推断，必须写出推断依据 |
| `未发现` | 未找到任何证据 | 未找到入口、实现、测试或数据访问代码 |

### 4.2 时效状态（freshness）

**由 Git 机械判定，不是模型判断**，取值只有三个：

| 时效状态 | 含义 |
|----------|------|
| `最新` | 该条证据相关文件与符号，在「最后验证版本」commit 与当前状态（HEAD + 工作区）之间没有变化 |
| `⚠ 可能过期` | 上述范围内存在变化，且该条本次未重新验证 |
| `未发现（无 Git 基线）` | 无 Git 或无有效 HEAD，无法做时效判定（见 4.4） |

**第一步：确定变更文件集（必须包含未提交修改）**

变更文件集 = **提交部分** ∪ **工作区部分**：

| 部分 | 命令 | 覆盖范围 |
|------|------|----------|
| 提交部分 | `git diff --name-status -M <base>..HEAD` | 基线之后已提交的变更，`-M` 用于检测重命名 |
| 工作区部分 | `git status --porcelain` | 已暂存、未暂存、未跟踪（`??`）的变更 |

> **不能只看 `<base>..HEAD`**：代码可能已经改完但尚未提交，只比较 commit 会漏判过期，工作区部分必须一并纳入。
> 未跟踪文件只在本次分析范围内才计入；跳过 `.gitignore` 忽略项与默认跳过目录（依赖、构建产物、缓存等）。

**第二步：多层影响判定**（命中任意一层即判受影响，并记录命中依据）：

| 层 | 判定方式 |
|----|----------|
| a. 路径层 | 变更文件 ∩ 该条「源码证据」路径 |
| b. 符号层 | diff 中修改/新增/删除的符号 ∩ 该条「核心执行流程」调用链符号、「源码证据」符号列 |
| c. 数据层 | 变更涉及的表名/字段名/迁移 ∩ 该条「数据变化」 |
| d. 接口层 | 变更涉及的路由/接口/入口签名 ∩ 该条「触发入口」 |
| e. 配置层 | 变更涉及的配置项/环境变量 ∩ 该条「外部影响」「前置条件」 |
| f. 测试层 | 变更涉及的测试文件 ∩ 该条「相关测试」→ 标记「测试证据待复核」（业务逻辑未必失效） |
| g. 重命名/删除 | 证据文件被重命名 → 「路径失效需修复」；被删除 → 「证据文件已删除，需重新验证或废弃该条目」 |

**额外报告**：若变更文件是某 BL 调用链中符号的定义文件，但不在该 BL「源码证据」里 → 标注「证据清单缺失，需补全」。

**第三步：得出结论**

命中任意一层且该条本次未重新验证 → 时效状态置 `⚠ 可能过期`；全部未命中 → 时效状态为 `最新`。

辅助命令：`git rev-parse HEAD`（当前基线）、`git log --oneline <base>..HEAD`（改动概览）、`git status --porcelain`（未提交变更）、`git rev-list --count HEAD`（版本号第四段）、`git log -1 --format=%an`（Git 提交作者）。

### 4.3 两个字段相互独立

- 证据状态与时效状态是**互相独立**的两个字段，**严禁混用、严禁合并书写**：`已验证` 表示「当时读到过实现」，不代表内容没过期；`⚠ 可能过期` 表示「代码改过了」，不代表当初的证据是错的。
- 知识地图用**两列分别显示**：`| ID | 业务能力 | 描述 | 证据状态 | 时效状态 |`，证据状态列只写四选一取值，时效状态列只写三选一取值。
- **严禁**把两个状态合并到同一列或同一行书写：不得用前缀、斜杠、括号等方式把证据状态与时效状态拼成一条，两者必须各占一列或各占一节。
- BL 条目内同样分节书写：「13. 证据状态」与「14. 时效状态」各写各的。

### 4.4 无 Git 或无有效 HEAD 的降级

- 不做时效判定，时效状态记 `未发现（无 Git 基线）`。
- 在知识地图「验证基线」章节说明时效判定不可用，并说明**每次运行需全量复核**。
- **不得编造 commit 哈希**，也不得用日期、文件时间戳冒充 commit。

### 4.5 增量维护基线

- **全局基线**：写在 `00-项目知识地图.md` 的「验证基线」章节，字段为 `last_verified_commit` + 验证日期。
- **单条基线**：写在每个 BL 条目的「最后验证版本」章节，字段为 Git commit + 验证日期。
- 增量更新时，只复核受影响的条目（按 4.2 的多层判定），未受影响条目的「最后验证版本」保持原值，不刷新为当前 HEAD。
- 每次增量分析结束后，在知识地图「验证基线」的「最近一次增量分析」中记录：基线 commit、分析日期、变更文件数（含未提交）、受影响 BL、已重新验证的 BL、仍标记过期的 BL。
- 变更文件集必须包含未提交修改（`git status --porcelain`），**不得只比较 `<base>..HEAD`**。

### 4.6 禁止事项

- **禁止把模型推断包装成事实**：推断内容必须显式标注 `状态：推断` 并写明推断依据，不得使用「系统会」「一定是」这类断言语气。
- 禁止编造业务事实、编造 commit 哈希、表名、接口、测试用例或业务规则；时效判定必须来自真实 Git 命令输出，**禁止在时效判定里编造 commit 哈希**。
- 禁止删除现有 7 套文档模板、大规模重命名、引入运行时依赖，禁止引入数据库、Web UI、RAG 或向量数据库。

## 五、追溯性正反例

### 5.1 业务规则

- ❌ 不能只写：「系统会检查用户权限。」
- ✅ 应写成：「系统在 `PermissionService.checkPermission()` 中检查当前用户是否具有该资源的操作权限。」

### 5.2 调用链

- ❌ 不能只写：「调用订单服务完成取消。」
- ✅ 应写成：`OrderController.cancel()` → `OrderService.cancelOrder()` → `Order.cancel()` → `InventoryService.release()` → `OrderRepository.save()`

### 5.3 数据变化

- ❌ 不能只写：「更新订单状态。」
- ✅ 应写成：`orders.status: PENDING_PAYMENT → CANCELLED`，同一事务内同时更新 `orders.updated_at`。

### 5.4 测试

- ❌ 不能只写：「已有单元测试覆盖。」
- ✅ 应写成：「`tests/order/cancel.spec.ts` → `should cancel pending order` 覆盖正常取消路径。」（未找到测试时写「未发现对应自动化测试。」）

### 5.5 推断标注

- 只能靠结构推断时（例如只看到 `XxxRepository` 命名而没读到实现），必须显式标注 `状态：推断`，并写明推断依据（目录结构 / 命名 / 配置项 / 迁移脚本）。
- 推断内容不得写入「源码证据」表的 `路径 → 符号` 列冒充直接证据；如需保留，另起一行标注「（推断）」。
