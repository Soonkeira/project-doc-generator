# 项目文档生成器 · 中文完整文档

## 1、项目定位

**项目文档生成器**（`project-doc-generator`）从现有代码结构、业务逻辑、API、数据库、调用关系和测试中，反推出一个**可查询、可追溯、可持续维护的项目知识体系**。

**知识层是核心，传统 7 套标准文档只是知识层的不同展示视图。** 知识层回答「系统是怎么工作的？」；传统文档回答「项目按照软件工程标准应该如何描述？」，内容以知识层为事实来源。7 套文档完整保留，不删除、不重命名。

知识层由**项目知识地图**、**源码索引**与 **BL 业务逻辑条目**三部分组成：知识地图从业务域索引到 BL 条目，源码索引从源码反查到 BL 条目，两者共同构成 BL ↔ 源码的**双向索引**。因此知识层既能回答「这个业务是怎么实现的」，也能回答「这段代码属于哪个业务」。

`Source Code → 代码与业务分析 → 项目知识层 → 传统 7 套项目文档`

业务问题可以沿下面这条链路反查到源码位置：

```
业务问题 → 业务能力 → 业务规则 → 入口/API → 调用链 → 数据变化 → 外部依赖 → 源码文件/符号 → 测试
```

它要回答的问题包括「这个功能是怎么实现的？」「为什么这里不能删除？」「订单取消以后做了什么？」「这个状态为什么会变化？」「这个接口最终修改了哪些数据？」「这个业务规则在哪段代码里？」。

> 上述问题及其中的业务名词均为**示例（占位，非项目事实）**，仅用于说明查询场景，不代表任何具体项目的真实业务规则。

## 2、核心能力

| 能力 | 说明 |
|------|------|
| 项目知识地图 | 按业务域索引全部业务能力，一个文件定位全项目主要业务逻辑；附验证基线与常见业务问题索引 |
| 业务逻辑反向分析 | 以业务问题为单位（而非代码文件为单位）组织结论，反推业务能力、触发入口、业务规则、关键分支与异常路径 |
| 源码证据追踪 | 每条重要结论都能反查到源码文件、符号、接口与表，并标注证据状态 |
| 业务调用链 | 记录 入口 → 应用服务 → 领域对象 → 仓储 → 外部依赖 的完整链路 |
| 数据影响分析 | 说明一段业务逻辑最终改动了哪些表、字段、缓存、消息与文件 |
| 源码反向索引 | 从源码反查业务逻辑（原来只有 BL → Source 单向）：汇总各 BL 的源码证据、数据变化、触发入口与外部影响，生成源码文件与符号 → BL、数据表/迁移 → BL、API/入口 → BL、配置项 → BL 四张反向索引表 |
| 双向索引一致性 | 源码索引必须与 BL 条目保持一致；不一致视为校验失败，需修正后才能推进验证基线 |
| 关系梳理 | 梳理 API / 数据库 / MQ / 外部服务之间的依赖关系 |
| Git 验证状态 | 记录知识地图的验证基线与每条 BL 条目的最后验证版本；时效状态由 Git 机械判定，与证据状态是两个独立字段 |
| 传统 7 套文档 | 以知识层为事实来源生成的标准化文档套件，兼容保留 |

## 3、输出结构

默认同时生成知识层与全部 7 份传统文档，输出到被分析项目的 `Doc/<项目名称>/` 下（`<项目名称>`、`<业务名称>` 为命名格式占位，生成时替换为真实名称）：

```
Doc/<项目名称>/
├── cn/
│   ├── 00-项目知识地图.md          # 业务能力索引 + 验证基线 + 常见业务问题索引
│   ├── 00-源码索引.md              # 源码 → BL 反向索引
│   ├── business/
│   │   └── BL-001-<业务名称>.md    # 业务逻辑条目（15 章节）
│   ├── 01-需求规格.md
│   ├── 02-概要设计.md
│   ├── 03-详细设计.md
│   ├── 04-数据库设计.md
│   ├── 05-API文档.md
│   ├── 06-测试计划.md
│   └── 07-部署手册与用户手册.md
└── en/
    ├── 00-Project Knowledge Map.md
    ├── 00-Source Index.md          # Source → BL reverse index
    ├── business/
    │   └── BL-001-<business-name>.md
    ├── 01-Requirement Specification.md
    ├── 02-Overview Design.md
    ├── 03-Detailed Design.md
    ├── 04-Database Design.md
    ├── 05-API Documentation.md
    ├── 06-Test Plan.md
    └── 07-Deployment & User Manual.md
```

知识层由 `00-项目知识地图.md`、`00-源码索引.md` 与 `business/BL-*.md` 组成；**源码索引与 BL 条目必须一致**，不一致视为校验失败。中英文编号一致，文件名一一对应。

## 4、业务逻辑条目结构

**编号规则**：`BL-` + 三位数字，按**首次建立顺序简单递增**：`BL-001`、`BL-002`、`BL-003`…，不再按业务域分段分配。编号永不复用、永不重排；条目删除后其编号作废，新条目取当前未使用的**最小编号**。同一业务逻辑在中英文下编号一致。

**业务域改为 metadata**：业务域写在 BL 条目头部的 `**业务域**：<业务域名称>` 字段中。业务域重新分类**只改这个字段，绝不改 ID**。知识地图仍按业务域分组展示，但分组标题**不得带编号范围**。

**固定章节**：每个 BL 条目必须包含以下 15 个章节，顺序与标题逐字一致，不得增删、改名或调整顺序。

| # | 章节 | 填写要求 |
|---|------|----------|
| 1 | 业务说明 | 从业务视角说明该业务解决什么问题、对谁有价值、在什么场景被使用 |
| 2 | 触发入口 | 真实入口：HTTP API / RPC / CLI / 定时任务 / MQ Consumer / Event Handler / UI 操作 / 内部方法调用；无证据时写「未发现」 |
| 3 | 前置条件 | 执行前必须满足的真实条件（数据状态、权限、外部系统可用性、配置开关） |
| 4 | 业务规则 | 允许或拒绝执行的条件、状态转换条件、权限要求、数值与生命周期限制 |
| 5 | 核心执行流程 | 真实调用链，逐层列出到数据访问层为止；禁止笼统描述 |
| 6 | 关键分支 | 真正影响业务行为的 if / switch / 状态机 / 异常分支及其走向差异 |
| 7 | 数据变化 | 修改哪些表与字段、创建或删除什么数据、状态如何变化、是否有事务 |
| 8 | 外部影响 | MQ / Redis / 第三方 API / 文件系统 / 缓存 / 对象存储等；没有则写「未发现」 |
| 9 | 异常与失败路径 | 只写已验证的异常条件与处理结果 |
| 10 | 源码证据 | 表格两列（类型、来源）；类型含 Controller / Service / Domain / Repository / Model / 表 / 配置项，来源写成 `路径 → 符号` |
| 11 | 相关测试 | 真实测试文件与测试方法；没有则写「未发现对应自动化测试。」，禁止虚构测试 |
| 12 | 关联业务 | 关联的 BL 编号与名称（上游触发、下游依赖、共享数据） |
| 13 | 证据状态 | 四选一，见下表 |
| 14 | 时效状态 | 三选一，见下表；由 Git 机械判定，与证据状态相互独立 |
| 15 | 最后验证版本 | Git commit + 验证日期（单条基线）；无 Git 时写「未发现（无 Git 基线）」 |

**两个互相独立的字段**，严禁混用、严禁合并成一条显示：

| 字段 | 判定方式 | 取值 |
|------|----------|------|
| 证据状态 | 模型判断（四选一） | `已验证` / `部分验证` / `推断` / `未发现` |
| 时效状态 | Git 机械判定（三选一） | `最新` / `⚠ 可能过期` / `未发现（无 Git 基线）` |

知识地图索引表固定用**两列分别显示**，列顺序为 `| ID | 业务能力 | 描述 | 证据状态 | 时效状态 |`；不得把时效标记拼在证据状态前面，也不得以任何形式合并成一条。

`已验证` 表示「当时读过实现」，不代表内容仍然新鲜；`⚠ 可能过期` 表示「代码已变化」，不代表原证据有误。

## 5、运行模式

| 模式 | 触发方式 | 流程 |
|------|----------|------|
| 生成模式 | `$project-doc-generator 生成当前项目的完整项目文档`；或说「形成项目文档」「生成项目文档」 | 全量扫描代码 → 提取业务知识 → 获取版本信息 → 建立知识层（知识地图 + 源码索引 + BL 条目）→ 以知识层为事实来源生成 7 套传统文档（写入）→ 生成后校验 |
| 查询模式（默认只读） | 直接提出业务问题 | 只读知识地图、源码索引与 BL 条目，定位相关条目后沿调用链、业务规则、数据变化与源码证据作答，**不写任何文件**；条目缺失或可能过期时明确告知「以源码为准」，并建议运行同步模式 |
| 同步模式（增量维护） | 要求做增量同步，例如「同步项目文档」「同步知识层」「更新项目知识层」 | 变更影响分析 → 只重新验证受影响的条目 → 刷新时效状态 → 更新源码索引 → 推进验证基线；只写知识层，不改 7 套传统文档 |

查询模式默认只读，不会因为提问而改写任何文件。同步模式只维护知识层（知识地图、源码索引与 BL 条目）；7 套传统文档需重新运行生成模式才会刷新。

## 6、Git 增量维护与过期检测

1. **首次运行**：全量扫描代码，建立知识地图、源码索引与全部 BL 条目；用 `git rev-parse HEAD` 取当前 commit，写入知识地图「验证基线」的 `last_verified_commit` 与验证日期。
2. **后续运行（变更文件集）**：读取已有 `last_verified_commit`，变更文件集 = **提交部分 ∪ 工作区部分**：
   - 提交部分：`git diff --name-status -M <last_verified_commit>..HEAD`
   - 工作区部分：`git status --porcelain`（覆盖已暂存、未暂存与未跟踪 `??`）

   **不能只看 `<last_verified_commit>..HEAD`**：代码可能已改但尚未提交，只比 commit 区间会漏判过期。
3. **变更影响分析（多层判定）**：不能只做文件路径交集，按下列各层判定，命中任意一层即判该条目受影响并记录依据：
   - 路径层：变更文件 ∩ BL「源码证据」路径
   - 符号层：变更的符号 ∩ 调用链符号
   - 数据层：表名 / 字段 / 迁移 ∩ BL「数据变化」
   - 接口层：路由 / 入口签名 ∩ BL「触发入口」
   - 配置层：配置项 ∩ BL「外部影响」「前置条件」
   - 测试层：测试文件 ∩ BL「相关测试」→ 标记「测试证据待复核」
   - 重命名 / 删除：路径失效需修复；证据文件已删除需重新验证
4. **只重新验证受影响的条目**：不整体重写文档，未受影响的条目保持原样（不改写内容、不重排编号）；每条 BL 另有自己的「最后验证版本」commit。
5. **刷新时效状态与源码索引**：受影响条目重新验证后更新其「时效状态」；并把源码证据、数据变化、触发入口与外部影响的变化同步到 `00-源码索引.md`，保持源码索引与 BL 条目一致。
6. **过期判定**：某条「源码证据」中的文件在该条「最后验证版本」commit 之后被修改（**含未提交修改**），且该条本次未重新验证 → 时效状态置 `⚠ 可能过期`；否则为 `最新`。
7. **基线更新**：全部受影响条目重新验证完成后，才把知识地图的 `last_verified_commit` 更新为当前 HEAD。
8. **记录「最近一次增量分析」**：知识地图中记录本次分析时间、基线 commit、变更文件数、受影响条目、判定依据与未处理项。
9. **降级**：无 Git 或无有效 `HEAD` 时不做时效判定，时效状态记 `未发现（无 Git 基线）`，并说明每次运行需全量复核；基线提交不可达（浅克隆、rebase、force-push）时降级为全量复核并说明原因。**不得编造 commit 哈希。**

## 7、使用方式

- 直接调用：`$project-doc-generator 生成当前项目的完整项目文档`
- 自然语言触发：「形成项目文档」「生成项目文档」；直接提出业务问题则进入查询模式
- 默认分析当前工作区；用户提供项目路径时以该路径为准
- 可指定语言（中文 / 英文 / 双语）、文档编号（如 `01,05`）、输出目录、作者、是否覆盖
- 未指定时生成知识层 + 全部 7 份传统文档；也可以只生成知识层、只生成传统文档，或指定编号子集
- 目标文档已存在时，先列出冲突文件并请求确认，不直接覆盖

**作者字段**按四级优先级获取：① 用户明确提供的作者 → ② 默认作者 `Soonkeira` → ③ Git 提交作者（`git log -1 --format=%an`）→ ④ 置空。严禁把机器账户名（`$env:USERNAME` / `whoami`）当作作者。

**版本号**：有 Git 时为 `1.{yy}.{Mdd}.{git提交次数}`（如 `1.26.509.1234`），无 Git 时为 `1.{yy}.{Mdd}.{hmm}`（如 `1.26.509.1430`）。每份文档头部包含项目名称、作者、日期、版本与变更日志。

## 8、边界与安全规则

| 规则 | 内容 |
|------|------|
| 目录边界 | 默认跳过 `.git/`、`node_modules/`、`vendor/`、`dist/`、`build/`、`coverage/`、`.venv/`、缓存与生成物目录 |
| 敏感信息 | 不读取或写入密钥、令牌与证书；跳过 `.env*`、`*.pem`、`*.key`、`credentials*`、`secrets*`；文档中只写配置项名称，不写值 |
| 修改范围 | 只修改用户指定的文档输出目录，不改源代码、配置、依赖锁文件或 Git 历史 |
| 禁止编造 | 未发现的数据库、API、测试或部署信息写明「未发现/不适用」，禁止编造表、接口、用例或运行参数 |
| 禁止包装推断 | 只能靠结构推断时必须显式标注 `状态：推断`；**禁止把模型推断包装成事实** |
| 示例标注 | 模板中的示例必须标注为「示例（占位，非项目事实）」 |
| 大仓库 | 代码库过大时先说明分析范围，优先读取入口、配置、路由、领域模型、数据库迁移、测试与部署文件 |
