# 项目知识层模板（v1.2.0）

> **定位**：知识层是核心，传统 7 套文档（01–07）只是知识层的不同展示视图。7 套文档模板见 `references/cn/document-templates.md`，其文件名、编号、路径保持不变。
>
> **追溯链路**：
>
> ```
> 业务问题 → 业务能力 → 业务规则 → 入口/API → 调用链 → 数据变化 → 外部依赖 → 源码文件/符号 → 测试
> ```
>
> **作者获取优先级**：以 `SKILL.md` 的「作者信息获取」章节为唯一权威（四级：① 用户明确提供的作者 → ② 本地默认作者 `Soonkeira`（https://github.com/Soonkeira） → ③ Git 提交作者 `git log -1 --format=%an` → ④ 置空）。**严禁**把机器账户名（`$env:USERNAME` / `whoami`）当作作者。
>
> **示例标注**：本文件模板中的所有示例内容均为占位示例，必须明确标注「示例（占位，非项目事实）」，实际生成时替换为真实分析结果。
>
> **本文件包含**：
> 1. 知识地图模板 `00-项目知识地图.md`
> 2. 业务逻辑条目模板 `business/BL-<NNN>-<业务名称>.md`
> 3. 状态定义与判定规则
> 4. 追溯性正反例
> 5. 示例内容标注规则

## 三、状态定义与判定规则

### 3.1 证据状态（evidence status）

**由模型判断**，每个 BL 条目与知识地图中的每条索引**只能四选一**：

| 证据状态 | 含义 | 判定依据 |
|----------|------|----------|
| `已验证` | 已从源码中直接确认 | 有明确源码证据（文件 → 符号），调用链、数据变化、分支均已读到对应实现 |
| `部分验证` | 主要结论已确认，部分环节未确认 | 核心链路已确认，但分支、异常、外部影响或数据变化中有未读到实现的部分 |
| `推断` | 由命名、目录结构、配置或文档推断 | 未找到直接实现证据，只能靠结构或命名推断，必须写出推断依据 |
| `未发现` | 未找到任何证据 | 未找到入口、实现、测试或数据访问代码 |

### 3.2 时效状态（freshness）

**由 Git diff 机械判定，不是模型判断**，取值只有两个：

| 时效状态 | 含义 |
|----------|------|
| `最新` | 该条「源码证据」中的文件在「最后验证版本」commit 与当前 HEAD 之间没有修改 |
| `⚠ 可能过期` | 上述文件集合中存在修改，且该条本次未重新验证 |

**判定规则（逐条执行）**：

1. 取该 BL 条目「最后验证版本」中的 commit 作为基线 `<base>`。
2. 执行 `git diff --name-status <base>..HEAD`，得到基线之后被修改的文件列表。
3. 将第 2 步的文件列表与该条「源码证据」中列出的文件集**求交集**。
4. 交集非空，且该条本次未重新验证 → 时效状态置 `⚠ 可能过期`；交集为空 → 时效状态为 `最新`。

辅助命令：`git rev-parse HEAD`（当前基线）、`git log --oneline <base>..HEAD`（改动概览）、`git rev-list --count HEAD`（版本号第四段）、`git log -1 --format=%an`（Git 提交作者）。

### 3.3 两个字段相互独立

- 证据状态与时效状态是**互相独立**的两个字段，**严禁混用**：`已验证` 表示「当时读到过实现」，不代表内容没过期；`⚠ 可能过期` 表示「代码改过了」，不代表当初的证据是错的。
- 知识地图「状态」列显示的是**证据状态**；若该条时效状态为可能过期，则在证据状态前加 `⚠ 可能过期`（如 `⚠ 可能过期 部分验证`）。

### 3.4 无 Git 或无有效 HEAD 的降级

- 不做时效判定，时效状态记 `未发现（无 Git 基线）`。
- 在知识地图「验证基线」章节说明时效判定不可用，并说明**每次运行需全量复核**。
- **不得编造 commit 哈希**，也不得用日期、文件时间戳冒充 commit。

### 3.5 增量维护基线

- **全局基线**：写在 `00-项目知识地图.md` 的「验证基线」章节，字段为 `last_verified_commit` + 验证日期。
- **单条基线**：写在每个 BL 条目的「最后验证版本」章节，字段为 Git commit + 验证日期。
- 增量更新时，只复核基线之后被改动过的条目（按 3.2 的交集判定），未改动条目的「最后验证版本」保持原值，不刷新为当前 HEAD。

### 3.6 禁止事项

- **禁止把模型推断包装成事实**：推断内容必须显式标注 `状态：推断` 并写明推断依据，不得使用「系统会」「一定是」这类断言语气。
- 禁止编造 commit 哈希、表名、接口、测试用例或业务规则。
- 禁止删除现有 7 套文档模板、大规模重命名、引入运行时依赖，禁止引入数据库、Web UI、RAG 或向量数据库。

## 四、追溯性正反例

### 4.1 业务规则

- ❌ 不能只写：「系统会检查用户权限。」
- ✅ 应写成：「系统在 `PermissionService.checkPermission()` 中检查当前用户是否具有该资源的操作权限。」

### 4.2 调用链

- ❌ 不能只写：「调用订单服务完成取消。」
- ✅ 应写成：`OrderController.cancel()` → `OrderService.cancelOrder()` → `Order.cancel()` → `InventoryService.release()` → `OrderRepository.save()`

### 4.3 数据变化

- ❌ 不能只写：「更新订单状态。」
- ✅ 应写成：`orders.status: PENDING_PAYMENT → CANCELLED`，同一事务内同时更新 `orders.updated_at`。

### 4.4 测试

- ❌ 不能只写：「已有单元测试覆盖。」
